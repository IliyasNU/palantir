# Аудит и проверка BiletFlow

7 ноября 2026, Asia/Qyzylorda. Исходная проверка охватывает [backend `26d0dbd`](https://github.com/IliyasNU/palantir/tree/26d0dbd58aaea5fc44d63144155d14fdeb8ad67a), [frontend `e41c821`](https://github.com/IliyasNU/palantir/tree/e41c821eaea181bf1648cdd88934c27a740186b7), [web с исправлением диагностики `52e4254`](https://github.com/IliyasNU/palantir/tree/52e425442f3bde335077c00e3cdfb89c9e7d18f6) и [mobile `314658b`](https://github.com/IliyasNU/palantir/tree/314658bc0ea7c2955405a0a4bb9f7969f2284441). Три родительских коммита интеграции сохраняют историю. Запуск обоих клиентов и API описан в [корневом README](../README.md).

`main` на момент аудита содержал README и `.gitignore`. `recovery/backend`, `feature/frontend` и `feature/iliyas-mobile-checkin` содержали старый backend без билетов и check-in. Backend `26d0dbd` включает FastAPI, SQLAlchemy, Alembic 0001–0002, bcrypt и PyJWT. Web использует React, TypeScript, Vite, npm lockfile и Playwright. Mobile использует Expo SDK 57, React Native, TypeScript, npm lockfile и ESLint.

## Контракт и реальные результаты

`POST /auth/register` принимает `email`, `full_name`, `password`, `role: "attendee"`. На реальной PostgreSQL браузер получил 201 с профилем и 409 при повторе. `POST /auth/login` получил 200 с токенами, неверный пароль получил 401, `GET /auth/me` с access token получил 200. Выход очищает сессию на клиенте. Серверные права проверяются при каждом защищённом запросе. UI отклонил невалидный пароль, а реальный backend вернул 422 для недопустимых данных в отдельном e2e. В тесте восстановления реальный отказ соединения не получил HTTP-статус, повтор с той же формы после запуска API завершился регистрацией и входом.

Web получил билет 201, повторный запрос вернул тот же билет 200. Чужой билет дал 404. Независимый PNG-декодер сравнил отображённый QR с точным `qr_payload` ответа. Владелец открыл билет после продажи последнего места. Отменённый билет остался в списке без QR.

## Повторить реальный web-прогон

Запустите выделенный API на localhost:8000, проверьте его PostgreSQL и освободите localhost:5173 для Playwright. Из `web` установите `RUN_LIVE_AUTH=1` и `RUN_LIVE_TICKETS=1`, затем выполните `npm run test:browser`. Для ticket и recovery нужны `ENVIRONMENT=test` и локальный `DATABASE_URL` с базой `biletflow_test`. Для recovery остановите свой тестовый API, оставьте PostgreSQL, задайте `CI=true`, `RUN_LIVE_RECOVERY=1` и `BILETFLOW_TEST_PYTHON` с путём к Python тестового backend. Передайте тестовый `JWT_SECRET_KEY` в окружении и выполните `npm run test:browser -- auth-recovery.live.spec.mjs`. Сценарий поднимает и останавливает собственный API. Тестовые env и результаты остаются локальными.

## Оставшаяся работа команды

1. Владелец backend подтверждает настройки реального окружения, миграции и безопасный ключ. Владелец репозитория восстанавливает GitHub Actions и проверяет интеграционный job на PostgreSQL 16.
2. Санжар проверяет кнопки получения и открытия билета, отмену и отсутствие мест на интеграционной ветке. Публичный frontend использует выданный командой HTTPS URL API и согласованный CORS origin.
3. Владелец mobile проходит [проверки на устройстве](../mobile/README.md#phone--integration-checklist) на той же базе. Камера должна считывать реальный QR, повтор после потерянного ответа сохраняет request_id, второй независимый скан отклоняется. Отдельно проверить права сотрудника, отменённое событие, фон и возврат приложения.
4. Команда mobile проверяет обновления SDK по advisory, повторяет npm audit, тесты и сборки. Остальные улучшения схемы и пагинации обсуждаются после приёмки основного сценария.

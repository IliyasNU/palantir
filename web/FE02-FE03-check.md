## Реализовано

- FE02: публичный `GET /events`, название/дата/место/ссылка, локальный поиск по части названия с `trim()` и без учёта регистра. Запрос не содержит `q` и авторизации. Загрузка, пустой каталог, отсутствие совпадений и ошибка с повтором разделены.
- FE03: `GET /events/{id}`, описание, местное время, место, статус и `Math.max(0, capacity - tickets_issued)`. Некорректные или отсутствующие счётчики означают неизвестную доступность. Есть 404, повтор, отмена и отсутствие мест; поздний ответ предыдущего ID игнорируется. Сохранён безопасный возврат после входа.
- Используются существующие API-клиент, `useAuth().request()` и `safeReturnTo`. App.tsx и авторизация не переписаны.
- `EventActions` получает `event`, `remainingSeats`, `returnTo`. Сейчас компонент пустой; место подключения сохраняется даже у заполненного или отменённого события.

## Зависимости и оставшаяся приёмка

**Команда backend:** нужен работающий API с контрактом `26d0dbd5` из `feature/temirlan-tickets-checkin`, разрешающий origin `http://localhost:5173`. Эта версия backend не объединена с текущей веткой; запуск старого checkout сам по себе не добавит публичный каталог. В исходниках указанного коммита подтверждено, что каталог фильтрует только `published`, а опубликованные и отменённые детали доступны гостю. Это проверка кода, не работающего сервера.

Для сценария №10 команда должна предоставить разрешённый аккаунт владельца/администратора и предназначенный для тестов черновик, который можно опубликовать и окончательно отменить. Для реального входа также нужен разрешённый тестовый аккаунт. Такие данные в текущем запросе не указаны; случайные мероприятия использовать нельзя.

**Санжар:** получение билета, открытие ранее полученного билета, страницы билетов и QR. Нужно подключить его компонент к `src/events/EventActions.tsx`. Нулевой остаток не должен блокировать переход к уже имеющемуся билету. Эти действия данной проверкой не подтверждены.

После восстановления окружения повторить на реальном API:

1. Убедиться, что `/health` и `/openapi.json` отвечают успешно и описывают публичные `/events` и `/events/{id}`. Настроить `web/.env.local`, затем из `web/` запустить `npm run dev` на localhost:5173.
2. В чистом окне браузера открыть `/events`: должны загрузиться карточки без входа. В Network проверить GET без Authorization и без `q`. Ввести часть названия существующей карточки в другом регистре с пробелами по краям, затем заведомо отсутствующую строку: ожидается «Ничего не найдено».
3. Открыть выбранное `/events/<id>` прямой ссылкой, обновить страницу; сверить название, дату, место, описание, статус и остаток с ответом API. Для подтверждённо отсутствующего числового ID ожидать «Событие не найдено».
4. На странице события перейти «Войти и вернуться к этому событию». Проверить login → register → login, затем войти разрешённым тестовым аккаунтом: адрес должен вернуться на `/events/<id>`.
5. В DevTools открыть Network request blocking, заблокировать только запросы к API `/events*`, обновить страницу. Ожидать ошибку, а не пустой каталог. Убрать блокировку и нажать «Повторить»: должны загрузиться данные. Повторить для деталей. Общий сервер не останавливать.
6. В режиме устройства задать ширину 375 px. Проверить каталог, поиск, детали и ошибки: текст и кнопки доступны, горизонтальной прокрутки нет.
7. Только для согласованного тестового черновика: проверить отсутствие его ID в гостевом каталоге. Под разрешённым аккаунтом владельца/администратора через штатный интерфейс/API выполнить `POST /events/<id>/publish`. Обновить гостевой каталог: событие должно появиться. Затем выполнить `POST /events/<id>/cancel`, обновить каталог: событие должно исчезнуть. Открыть прямую ссылку: детали должны показать отмену. Авторизацию можно выполнить через Swagger `/docs`, если он включён. Токены не сохранять в отчётах и скриншотах. Отменённое событие повторно опубликовать нельзя по этому контракту.

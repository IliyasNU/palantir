## Что реализовано и что изменено

В общей базе уже были каталог, подробности, EventActions, выдача, страницы билетов и QR. Сохраняется существующий API-клиент и useAuth().request(). Повторно авторизация, выдача или QR не реализовывались.

Ранее в этой ветке исправлены только два подтверждённых пробела:
1. Для гостя на полном/отменённом событии подпись действия — «Войти и проверить мои билеты»; существующий билет остаётся доступен.
2. В существующем ticketErrorMessage понятные русские сообщения 401/403. 401 очищает общую сессию и предлагает вход; 403 сохраняет её.

Whitelist returnTo уже точно соответствовал существующим маршрутам /events, /events/:id, /tickets, /tickets/:id. Добавлены проверки, переносить или переписывать его не потребовалось.

В текущем live-прогоне **новых ошибок приложения в области Алиби не обнаружено**. Добавлена проверочная инфраструктура внутри web: выбор локального API для существующих auth/ticket live-тестов, защита тестовой БД, общий live-конфиг и сценарий жизненного цикла. Ошибки первоначального запуска (фильтр выбора Playwright и обработка предупреждения Node в PowerShell) относились к тестовому запуску, не к приложению.

## Подготовка через API — отдельно от UI

Через существующие HTTP API создавались только уникальные тестовые организаторы и события в новой БД. Публикация и отмена выполнялись через API организатора; кабинет организатора этим не проверен. Регистрация посетителя, вход, выдача и открытие билета выполнялись через настоящие формы/кнопки UI.

- Dev: полный сценарий события **1**, билет **1**; существующий ticket live-тест — событие **2**, билет **2**.
- Production: полный сценарий события **3**, билет **3**; ticket live-тест — событие **4**, билет **4**.
- В рамках live-прогона создано **10 аккаунтов, 4 события, 4 билета**. Все четыре события завершили сценарий в состоянии cancelled. Ничего не удалялось.
- Повторная выдача проверена отдельно HTTP-запросом: **200, тот же ID**; UI открывает ранее полученный билет. Проверка SELECT в новой БД подтвердила по одной строке tickets на event_id и tickets_issued=1.
- Чужой посетителю билет скрыт как 404 — существующий live-тест.
- Сразу после live-прогона `GET /events` → **200 []**, потому что все четыре события прогона отменены. До отмены их появление подтверждено браузером.

Позднее по отдельному запросу Алиби опубликованы два демонстрационных события для записи интерфейса. Они не относятся к этой матрице приёмки; их данные и учётные данные организатора не включаются в Git. Ответ пустого каталога выше описывает момент окончания live-прогона.

## Повторение live-прогона в этом локальном окружении

Следующие пути и порты описывают **только выделенное окружение Алиби**, а не настройку всей команды. Перед запуском проверить mounts, ENVIRONMENT и БД; localhost сам по себе не доказывает изоляцию.

```powershell

Get-Content -LiteralPath "$runtime\.env" | ForEach-Object {
    $pair = $_ -split '=', 2
    if ($pair.Count -eq 2) { $settings[$pair[0]] = $pair[1] }
}
# Пароль остаётся в окружении процесса, не выводится.
$env:ENVIRONMENT = 'test'
$env:DATABASE_URL = 'postgresql://biletflow_test:' + $settings['POSTGRES_PASSWORD'] + '@127.0.0.1:5433/biletflow_test'
$env:BILETFLOW_LIVE_API_URL = 'http://localhost:8002'
$env:BILETFLOW_FRONTEND_SHA = (git rev-parse HEAD)
$env:BILETFLOW_BACKEND_SHA = 'c5b83a851128c486b1b15cebea94c6df8166308d'
$env:RUN_LIVE_AUTH = '1'
$env:RUN_LIVE_TICKETS = '1'
$env:RUN_LIVE_667 = '1'
```

## Что остаётся команде

- **Ильяс / телефон:** на согласованной тестовой LAN проверить доступ к /health с устройства, камеру/разрешения, скан настоящего QR, повторный скан без повторного check-in, невалидный/чужой QR, неназначенного сотрудника, отмену и потерю ответа/повтор. Нужны физический телефон, сотрудник и назначение на собственное новое тестовое событие. Текущий API привязан к loopback и телефону недоступен; LAN-настройки в этой работе не менялись. Все четыре события live-прогона отменены — для скана нужен отдельный согласованный опубликованный тестовый билет.
- **Хостинг:** на реальном URL открыть /events/:id и /tickets/:id в новой вкладке и обновить. HTTP-сервер должен отдать index.html для клиентских маршрутов. Адрес хостинга не предоставлен, проверка не выполнялась.
- **Backend:** подтверждённых ошибок в пройденных сценариях не выявлено. Естественный 403 закрытого билетного запроса требует отключённого аккаунта; существующего API управления этим состоянием для теста не использовали, БД не изменяли вручную.
- **Санжар:** блокера отсутствующего EventActions/выдачи/страницы билета нет. Его существующая функциональность прошла указанные live-тесты; кабинет организатора и все возможные билетные сценарии этим отчётом не сертифицируются.

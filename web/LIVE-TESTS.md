# Live-приёмка web: проверяемая изоляция

Команды запускаются из `web/` на Windows, Linux или macOS с установленными зависимостями проекта. Node.js запускает Playwright без привязки к PowerShell и личным абсолютным путям. Каталог, авторизация и билеты приложения не имеют тестового режима.

## Что требуется до запуска

1. Локальный Docker daemon (Unix socket или Windows named pipe). Удалённые Docker contexts не поддерживаются.
2. Явно выбранный **отдельный** Compose-проект с двумя работающими сервисами `backend` и `db`, PostgreSQL `biletflow_test`, `ENVIRONMENT=test`.
3. Backend из неизменённого образа без mounts, без `--reload`/других источников env; запуск `uvicorn app.main:app --host 0.0.0.0 --port 8000`. Публикация API только на 127.0.0.1, CORS для http://localhost:5173.
4. Собственный локальный volume `<project>_postgres_data`, принадлежащий этому Compose-проекту. Другой контейнер не должен использовать его; сеть содержит только эти backend и db. External/shared volumes, bind mounts БД и сетевые volumes отклоняются.
5. Полный локально доступный Git SHA исходников backend. Preflight сверяет `app/` и requirements с файлами образа; CRLF/LF нормализуются. Пароли БД, JWT и DATABASE_URL тестовому runner **не передаются**.

Инструкция создания базового Docker-проекта находится в [README репозитория](../README.md). Выберите свободные порты и новое имя проекта; не переиспользуйте общую БД. Для исключения bind mount и reload нужен локальный override, например `web/test-results/runtime/compose.override.yml` (игнорируется Git):

```yaml
services:
  backend:
    volumes: !reset []
    command: sh -c "alembic upgrade head && uvicorn app.main:app --host 0.0.0.0 --port 8000"
```

В отдельном приватном env проекта укажите сгенерированные POSTGRES_PASSWORD/JWT_SECRET_KEY, POSTGRES_DB=biletflow_test, ENVIRONMENT=test, свободные BACKEND_PORT/DB_PORT, API_BIND_HOST=127.0.0.1, CORS_ORIGINS=http://localhost:5173. Используйте оба Compose-файла, явный `-p` и `--env-file`. После проверки итогового `docker compose config` запускайте только собственный проект согласно README. Эти инструкции не разрешают удаление volumes, смену общей БД или запуск миграций на командном сервере.

Проверка уже работающего проекта выполняет **только inspect, чтение исходников и SELECT**. Никаких миграций или перезапуска контейнеров runner не делает. Она сверяет:
- origin API с опубликованным портом конкретного контейнера;
- project/network/mounts/volume и отсутствие другого потребителя volume;
- env реально запущенного процесса uvicorn и неизменность его `/app`;
- engine из существующего `app.db.session` с env этого процесса: адрес и имя БД;
- `pg_control_system().system_identifier` из этого подключения с идентификатором PostgreSQL в контейнере db;
- доступность `/health` по выбранному API.

Проверка привязки требует права SELECT на pg_control_system(); стандартный пользователь отдельного PostgreSQL из Compose обладает им. Если оно отсутствует, инспекция недоступна, env не совпадает или подключение ведёт в другую БД, live прекращается до регистрации организатора/подготовки событий. Один лишь DATABASE_URL в оболочке больше ничего не разрешает.

## Переносимый запуск

Пример для выделенного окружения Алиби. **8002 и имя проекта — пример, не обязательные настройки команды.** Замените их и SHA на проверенные значения своего отдельного окружения:

```sh
node scripts/run-live.mjs --api http://localhost:8002 --project biletflow-667-live --backend-ref c5b83a851128c486b1b15cebea94c6df8166308d --preflight-only
node scripts/run-live.mjs --api http://localhost:8002 --project biletflow-667-live --backend-ref c5b83a851128c486b1b15cebea94c6df8166308d --mode dev --channel msedge
node scripts/run-live.mjs --api http://localhost:8002 --project biletflow-667-live --backend-ref c5b83a851128c486b1b15cebea94c6df8166308d --mode production --channel msedge
```

Для установленного Chrome используйте `--channel chrome`; для установленного Playwright Chromium — `--channel chromium`. При отсутствии браузера сначала установите его по принятой в проекте инструкции.

`--preflight-only` подтверждает только backend/БД. В каждом live-тесте до первого POST дополнительно выполняется навигация браузера в /events с ожиданием **реального GET**. Его origin должен совпасть с проверенным backend. До завершения обеих проверок все browser writes заблокированы. После проверки допускаются записи только на выбранный origin; переадресация записи блокируется. HTTP-подготовка также ограничена этим origin и не следует redirect.

Production-запуск **всегда собирает новый dist** с выбранным VITE_API_URL перед preview. Переменная preview не используется как доказательство адреса старого dist. Занятый 5173 приводит к остановке, чужой сервер не переиспользуется. Запущенные runner frontend-процессы завершаются после тестов.

Полный live-прогон включает существующие auth, tickets и 667 тесты и создаёт 5 аккаунтов, 2 события и 2 билета в выделенной БД. Записи остаются там; события прогона отменяются через API своих организаторов. Отдельные демонстрационные мероприятия не изменяются.

## Проверки без БД

```sh
npm run typecheck
npm test
npx playwright test --config playwright.isolation.config.mjs
npm run test:browser -- --output test-results/mock-regression
```

Регрессия изоляции использует два локальных HTTP-приёмника без БД: старый dist указывает на A, выбран B. Mismatch и отсутствие backend proof не допускают ни одной записи; после свежего build запись разрешается только на B. Также проверяется блокировка 307 в сторону A. Это проверка защиты тестовой инфраструктуры, а не live-приёмка бизнес-функций.

Обычная регрессия не включает opt-in live-тесты. Не задавайте RUN_LIVE_* вручную для неё. При наличии таких переменных в своей оболочке удалите их или задайте 0.

## Evidence и границы

Каждый live-запуск получает отдельную папку `test-results/live/<mode>-<UTC time>-<run ID>/`. Там:
- `preflight.json` каждого теста: фактические API, browser type/channel/version/headless, SHA web, состояние всего дерева, fingerprint кода web, подтверждение backend/БД;
- `evidence.json` 667: то же окружение, время начала/окончания, конкретные публичные запросы и результат сценариев;
- снимки только страниц событий без QR и паролей.

SHA исходников backend означает проверенное соответствие исполняемых файлов выбранной Git-версии; **commit, из которого первоначально собран образ, не угадывается** и записывается `unknown`. Image ID записывается отдельно. Неопределимые сведения о Git/browser также равны `unknown`. Fingerprint web включает файлы кода/тестов/конфигурации и lockfile, исключает Markdown и env.

Токены, пароли, DATABASE_URL и QR-payload в evidence не записываются. В live отключены trace/video/автоматические screenshots и page snapshot при ошибке; сравнение QR не печатает его значение при несовпадении. Не публикуйте raw failure logs или все test-results целиком: общими артефактами должны быть проверенные preflight/evidence JSON и безопасные снимки. В частности, сборка dist и локальная конфигурация остаются локальными.

[Исторический отчёт 7 ноября](667-acceptance.md) сохраняется отдельно. [Доработки по ревью 8 ноября](667-review-2026-11-08.md) содержат новые результаты. Старый отчёт не является описанием текущего состояния тестовой БД.

Сетевой отказ 667 имитируется в браузере. 401 приходит от API на некорректный bearer; отказ 403 на запрещённую публикацию воспроизводится в билетном UI. Это не естественный 403 активного владельца билета и не проверка истечения JWT по времени.

Существующий GitHub Actions live-job использует прямой backend, а не описанную Docker-инспекцию. После этих изменений непроверенный запуск намеренно остановится. Workflow вне web в этой работе не меняется; команде нужно подключить поддерживаемое выделенное окружение, прежде чем объявлять этот live-job прошедшим. Локальные результаты не означают, что GitHub Actions выполнен.

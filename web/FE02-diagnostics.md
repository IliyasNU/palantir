## Подтверждённая причина HTTP 405

В отличие от предыдущего прогона из `FE02-FE03-check.md`, сервер теперь доступен, но предоставляет старый контракт событий.

- `loadEnv('development', ...)` даёт `VITE_API_URL=http://localhost:8000`.
- Работающий Vite на localhost:5173 внедряет тот же адрес в `src/api/index.ts`. Проверен фактически обслуживаемый модуль, а не только файл env.
- В `vite.config.ts` нет proxy. Каталог использует общий `api.request('/events', { signal })`: браузер отправляет **GET http://localhost:8000/events**, без `q`, тела и Bearer token.

| Проверка | Фактический ответ |
| --- | --- |
| GET `/health` | 200 |
| GET `/openapi.json` | 200 |
| OpenAPI: `/events` | Только `post`, метода `get` нет |
| GET `/events` с Origin localhost:5173 | 405, `Allow: POST`, `{"detail":"Method Not Allowed"}` |
| OPTIONS `/events` с Origin localhost:5173 и Access-Control-Request-Method: GET | 200, разрешён origin localhost:5173 |
| GET `/events` в Edge | 405; интерфейс получает HTTP-ошибку |

Таким образом, 405 относится к GET, а не к preflight. Текущий backend checkout также содержит POST `/events` без GET списка; работающий сервер соответствует этому старому контракту. Точный Git SHA запущенного сервера не установлен. В доступном коммите `26d0dbd5` публичный GET уже есть.

Это не ошибка выбора метода frontend. Замена GET на POST создавала бы событие и не является исправлением. Другой подтверждённый адрес актуального API не предоставлен, поэтому `.env.local` не изменён. Mock-данные в приложение не добавлены.

Для пользователя HTTP 405 теперь отображается как «Каталог недоступен на подключённом сервере (HTTP 405). Обратитесь к команде сервиса.» Кнопка «Повторить» сохранена; ошибка не превращается в пустой каталог.

## Подтверждённая причина блокировки поиска

У input стояло `disabled={state.kind !== 'success' || state.events.length === 0}`. Это запрещало ввод при загрузке, любом отказе API и успешном пустом списке.

До исправления проверка DOM в Edge показала: `disabled: true`, `readOnly: false`, родительского `fieldset[disabled]` нет, `pointer-events: auto`. Проверка `elementFromPoint` в центре поля подтвердила отсутствие перекрывающего элемента. Связка `value={query}` / `onChange={...setQuery(...)}` исправна.

Условие disabled удалено вместе с неиспользуемым CSS для disabled-поиска. Поле доступно независимо от результата загрузки. Состояние query не сбрасывается при повторе; после успешного ответа применяется прежний клиентский поиск с trim и без учёта регистра. Запрос `q` серверу не отправляется.

## Оставшийся блокер и безопасные варианты подключения

Нужен API с публичным каталогом из `26d0dbd5` или совместимой более новой версии. Варианты:

1. Получить у команды подтверждённый адрес сервера. Проверить `/health`, наличие GET `/events` в `/openapi.json`, сам гостевой GET и CORS для localhost:5173. После этого указать подтверждённый базовый URL в `web/.env.local` и перезапустить Vite.
2. Подготовить отдельный clone/checkout backend на нужном коммите, не переключая эту frontend-ветку. Запускать в отдельном окружении: другая БД, новый Docker volume, отдельные имена контейнеров/Compose project и свободные порты. Не подключать существующий volume и не выполнять на нём миграции. Проверить фиксированные container_name, порты и имена volumes в Compose: одного другого project name может быть недостаточно для изоляции. После успешной проверки OpenAPI и GET подключить frontend к фактическому адресу этого экземпляра.

Ни один вариант автоматически не запускался. Текущий backend и его данные не менялись; POST `/events` не вызывался.
